## 二、数据库说明（重要）

### 2.1 实际使用 `enterprise_hr`，而非 `hospital-bedside`

原始需求指定 `hospital-bedside`，但勘察发现该库是**另一套已存在的病房床旁系统**（26 张表：`patient` / `bed` / `ward` / `medical_order` 等），其中：

| 表名 | `hospital-bedside` 中的结构 | 本系统所需结构 | 冲突 |
|---|---|---|---|
| `sys_user` | `role_type` / `patient_id` / `staff_id`（21 行） | `username` / `employee_id` / `password` | **表名相同、结构完全不同** |
| `notice` | 床旁通知（5 行） | 人事公告（`notice_type` / `target_scope`） | **表名相同、结构完全不同** |

直接建表会**覆盖病床系统数据**。经确认改用 `enterprise_hr`：该库已有本项目完整的 **49 张业务表 + 演示数据**，现有实体类正是按它编写的，零冲突。`hospital-bedside` 保持原样未动。

数据库连接写在 `application.yml`，**支持环境变量覆盖**，需要指向其它库时无需改代码：

```yaml
url: jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:enterprise_hr}?...
username: ${DB_USER:root}
password: ${DB_PASSWORD:123456}
```

### 2.2 测试库与开发库物理隔离

集成测试的 `test-cleanup.sql` 会对约 40 张业务表做硬删除。为避免「跑一次 `mvn test` 就清空演示数据」，`application-test.yml` 固定指向独立的 `enterprise_hr_test`：

```bash
# 重建测试库（与开发库初始数据一致）
CREATE DATABASE enterprise_hr_test DEFAULT CHARACTER SET utf8mb4;
mysqldump -uroot -p123456 --single-transaction --default-character-set=utf8mb4 \
  enterprise_hr | mysql -uroot -p123456 --default-character-set=utf8mb4 enterprise_hr_test
```

> 注：`mysqldump` 必须**管道直传**给 `mysql`。若先重定向到文件再导入，数据中的 `\'` 转义会让客户端报
> `Unknown command '\''` 并**中途静默中断**（只建出前几张表）。

### 2.3 增量 DDL（本轮唯一的表结构变更）

本轮只对表结构做了一处**纯新增、可空**的变更，用于承载 BR-05-03 的核算人（原因见 §九 缺陷 6）：

```sql
ALTER TABLE salary_record
  ADD COLUMN calc_by BIGINT DEFAULT NULL COMMENT '核算人用户ID(须与复核人不同,BR-05-03)' AFTER lock_status;
```

已同步：`enterprise_hr_schema.sql`（建表脚本）、`enterprise_hr` 与 `enterprise_hr_test` 两个库、
`SalaryRecord` 实体、`SalaryRecordVO`（响应蛇形 `calc_by`）、`SalaryRecordServiceImpl`（写入改用该列）。

**向后兼容**：`calc_by` 为 `NULL` 时，复核校验会回退解析历史数据在 `remark` 中留下的 `CALC_BY=<userId>` 标记，
因此升级前已生成的薪资记录仍能被 BR-05-03 正确拦截，无需数据回填。

## 三、统一响应与统一异常

### 3.1 响应契约

响应体**严格**为三段式，无任何多余字段：

```json
{ "code": 200, "message": "success", "data": { ... } }
```

**HTTP 状态码与业务 `code` 同值**，便于网关与浏览器 Network 面板直接识别：

| code | 含义 | 典型场景 |
|---|---|---|
| 200 | 成功 | 正常返回 |
| 400 | 参数/业务校验失败 | 必填缺失、业务规则拒绝（BR-xx） |
| 401 | 未认证 | 缺少/非法/过期令牌，账号被停用 |
| 403 | 已认证但无权限 | 角色不足、越权访问他人数据 |
| 404 | 资源不存在 | 按 id 查询未命中 |
| 405 | 方法不支持 | 路径存在但 HTTP 动词不匹配 |
| 409 | 状态冲突 | 唯一键冲突、并发重复提交 |
| 500 | 服务端异常 | 未预期错误 |

### 3.2 统一异常通道

- 所有业务失败一律抛 `BizException`（携带 `ErrorCode` 枚举，共 **39 个**业务错误码），`GlobalExceptionHandler` 据 `code` 决定 HTTP 状态。
- 参数校验（`@Valid`）→ 400；`MissingServletRequestParameter` / 类型不匹配 → 400；`HttpRequestMethodNotSupported` → 405;`DuplicateKeyException` → 409；`DataIntegrityViolationException` → 400。
- **`IllegalArgumentException` 仅作遗留兜底**，统一按 400 处理；本轮已把员工模块中误用它的 13 处全部改为 `BizException`（其中「资源不存在」由错误的 400 纠正为 404）。

### 3.3 与前端异常处理的对应关系

前端 `src/utils/request.js` 的响应拦截器与本契约一一对应，本轮已修正其两个缺陷：

1. **错误分支原先只弹 `error.message`**（axios 的英文文案），拿不到后端的中文 `message` → 改为优先读 `error.response.data.message`。
2. 未区分 401/403 → 现在 401 走清令牌 + 跳登录，403 提示「没有操作权限」。

## 四、字段命名双向约定（最易踩坑处）

| 方向 | 约定 | 实现方式 |
|---|---|---|
| **响应** | 蛇形 `snake_case`（与数据库列名一致） | 实体/VO 标 `@JsonNaming(SnakeCaseStrategy)` |
| **请求体 / 查询参数** | 驼峰 `camelCase` | Req DTO **不标**注解 |

原因：前端 el-table 直接 `prop="emp_no"` 绑定响应；而表单提交的是 `{ deptId: 1 }`。全局启用蛇形会让请求体驼峰无法绑定，因此采用「响应侧注解、请求侧不注解」的双向方案。

**少数被前端已消费、必须保持驼峰的字段**（用 `@JsonProperty` 显式覆盖）：
`empNo`（员工创建结果）、`initPassword`、`totalHours`、`enrollCount`、`recordCount`、`enrolls`、`requestNo`、`planCode`、`contractNo`、`standardCode`、`checkinTime`、`checkoutTime`、`finalScore`、`grade`、`weightNote`、`created`；以及看板 `summary`/`charts` 的全部字段；登录响应 `data.user` 内部字段（`employeeId`/`realName`/`deptId`/`roles`）。

## 五、鉴权、权限与数据范围

### 5.1 自研 JWT（不引入 Spring Security 完整过滤链）

只引入 `spring-security-crypto` 使用 BCrypt，避免与既有代码产生过滤链冲突。

- 令牌算法 HS256（jjwt 0.12.6），密钥短于 32 字节**直接启动失败**（fail-fast，防止弱密钥上线）。
- 令牌只携带 `userId`，**角色每请求实时查库重建**（`sys_user → sys_user_role → sys_role`），保证停用账号、变更角色即时生效，不必等令牌过期。
- `AuthInterceptor` 覆盖 `/**`，**fail-close**：仅放行 `ehr.security.permit-urls`（`/auth/login`、Swagger）。未认证访问不存在的路径也返回 401，不泄露路径是否存在。
- `UserContext` 使用 `ThreadLocal`，在 `afterCompletion` 强制清理（容器线程复用会串用户）。

### 5.2 两级权限模型

1. **接口级**：`@RequireRoles`（方法级优先于类级，`ROLE_ADMIN` 默认全通过）。
2. **行级数据范围**：`DataScopeHelper` —— `1` 全部 / `2` 本部门 / `3` 本部门及下级 / `4` 仅本人 / `5` 自定义；多角色取**最宽**。例如 `EMPLOYEE` 查询员工列表只返回本人档案。

### 5.3 安全细节

- 登录失败**不区分「账号不存在」与「口令错误」**（防账号枚举）；连续失败 5 次锁定 30 分钟。
- 口令 BCrypt(10) 哈希存储；`SysUserVO` **不含** `password` 字段。
- 脱敏工具 `MaskUtil`：身份证保留前 6 后 2、银行卡保留前 4 后 4、手机号中间 4 位。
- 操作日志 `@OperLog(saveParams = false)` 默认不记录请求参数，避免口令等敏感信息入库。

## 六、系统级日志记录

| 日志表 | 写入时机 | 内容 |
|---|---|---|
| `sys_login_log` | 每次登录**成功与失败**都写 | 账号、IP（解析 `X-Forwarded-For` 链）、浏览器、操作系统、登录状态、提示信息 |
| `sys_oper_log` | 带 `@OperLog` 的写操作 | 模块、操作类型、操作描述、请求 URL/方法、耗时、结果 |

切面设计要点：

- `OperLogAspect` 环绕通知，**在 `finally` 中记录**：业务抛异常时先记「失败日志」再原样 `rethrow`，保证异常语义不变。
- **写日志失败永不阻断业务**（`try/catch` 吞掉落库异常）。
- 通过 `OperLogRecorder` 接口解耦：`common` 层只依赖接口，`system` 层提供 `DbOperLogRecorder` 落库实现，避免模块间反向依赖。

## 九、本轮修复的真实缺陷

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | 自动工号取号用 `selectObjs`，被 `@TableLogic` 追加 `deleted = 0`，看不到「已逻辑删除但仍占用 `uk_emp_no` 唯一键」的行 | 一旦有员工被逻辑删除，之后**所有入职办理都 409**；且重试逻辑空转 | 新增 `EmployeeMapper.selectMaxEmpNoSeq()` 原生 SQL 绕过逻辑删除注入 |

## 十一、设计取舍：已核实项与待确认项

### 11.1 已核实无风险（用代码/数据实查过，不需要产品侧再确认）

| 项 | 核实结论 | 证据 |
|---|---|---|
| `PUT /employees/{id}` 刻意不含 `status` | **安全**。员工新增/编辑表单字段只有：姓名、用工性质、部门、岗位、职级、基本薪资、手机号、邮箱、入职日期、学历 —— **没有状态字段**，不存在「提交成功但状态没变」的静默失败。状态只能走 `PUT /employees/{id}/status`，以便留异动痕迹（BR-02-04） | `views/employee/index.vue` 表单定义 |
| 前端是否会传 `empNo` | **不会**。视图只**读** `res.empNo`（创建结果，驼峰）与 `emp_no`（列表/详情，蛇形），与后端实现完全一致 | `grep -rn "empNo" views/ api/ store/` 仅命中一处读取 |
| `courseNames` 口径 | **实现正确**，无需产品确认。真实关系是 `training_plan ← training_enroll(plan_id, course_id) → course`；实现按该计划的报名课程去重、按课程 ID 升序以「、」连接，无报名记录时回退 `training_record`。已用接口返回值逐条比对库内 `GROUP_CONCAT` 一致 | `TrainingSupport#loadCourseNames` + 接口返回值 vs `GROUP_CONCAT` 比对 |
| 员工状态枚举取值 | **与前端字典一致**：`0` 离职 / `1` 在职 / `2` 试用 / `3` 待入职。`BizConst.EMPLOYEE_PENDING = 3`，与 `employee.status` 列注释、`src/dict/index.js` 的 `employeeStatus` 字典三方一致 | 三处交叉核对 |
| 薪资核算人 | **已修复**（见 §九 缺陷 6）：补 `salary_record.calc_by` 列，不再占用 `remark` | `docs/verify-api.py` §6.1 |
